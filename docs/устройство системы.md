# Как работает система (человеческим языком)

Короткая шпаргалка «зашёл — освежил в голове». Технические детали — в [ТЗ](PO-PLAN.md) и планах в [docs/plans](plans/).

## Одним взглядом

```
   ИСТОЧНИКИ (RSS + Telegram через RSSHub)
              │
        n8n (сбор)           ← нормализует айтем, ставит channelId/source/sourceLang
              │  POST /posts
              ▼
  ┌──────────────────────────── СЕРВИС аппрува (наш) ────────────────────────────┐
  │  ingested → [эмбеддинг+дедуп] → pending → [человек в админке] → ready_to_publish │
  │      │                             ▲                                 │         │
  │   дубль/ошибка          классификация, рерайт,                   превью в      │
  │      ▼                    правка, картинка,                      служебку      │
  │  rejected / failed            аппрув                            (file_id)      │
  └───────────────────────────────────────────────────────────────────┬──────────┘
                                                                        │  GET /posts/queue
                                                                        ▼
                                                                 n8n (публикация)
                                                                        │  постит в основной канал
                                                                        ▼   PATCH /posts/:id/published
                                                                    published
```

Ключевая идея: **сервис — единственный владелец состояния**. n8n ничего не хранит и не пишет в БД напрямую — только ходит в наш REST. Сбор и публикация — это два отдельных воркфлоу n8n по краям, а вся логика и хранение — посередине, у сервиса.

> ⚠️ **Статус:** сами n8n-воркфлоу (сбор RSS и публикация) **ещё не созданы** — со стороны сервиса готов только REST-контракт (`POST /posts`, `GET /posts/queue`, `PATCH /posts/:id/published`). Разделы 1 и 4 описывают этот контракт.

---

## 1. Что приходит от n8n (вход: `POST /posts`)

n8n собирает сырой айтем из фида, добавляет к нему **`channelId`** (какому каналу принадлежит), **`source`** (имя фида: rbc/guardian/bbc/…) и **`sourceLang`** (`ru`/`en`) и шлёт нам. Сырой айтем — это обычная RSS-карточка, из которой мы достаём:

| Что достаём | Из чего |
|---|---|
| **заголовок** (`origTitle`) | `title` |
| **текст** (`origText`) | `contentSnippet` → чистим от HTML, срезаем хвост «Continue reading…»/«Читать далее» |
| **автор** (`author`) | первое непустое из `creator` / `author` / `dc:creator`, иначе пусто |
| **категории** (`categories`) | приводим к плоскому списку строк (у RBC уже строки, у Guardian — из объектов, у BBC пусто) |
| **дата** (`pubDate`) | `isoDate` |
| **картинка(и)** (`images`) | `enclosure.url` → один кандидат; иначе первый `<img>` из `content`; иначе пусто (текстовый пост) |
| **ссылка** (`link`) | канонич. ссылка — ключ дедупа **в пределах канала** |

**Дедуп на входе — по ссылке в рамках канала.** Если та же пара (канал + ссылка) уже приходила — сервис отвечает `409` и карточку не заводит. Одна и та же ссылка в разных каналах — это ОК (один источник может кормить несколько каналов).

Новая карточка появляется в статусе **`ingested`** и сразу отдаётся ИИ-воркеру.

---

## 2. Что с карточкой делает ИИ-воркер

Работает асинхронно (не держит HTTP-ответ), обрабатывает карточки **строго по одной** (последовательная очередь — чтобы не было гонок дедупа). Ведёт карточку `ingested → processing → pending | rejected`. Автоматических шагов теперь два:

1. **Эмбеддинг** — считаем смысловой вектор текста (локальная Ollama, модель `bge-m3`).
2. **Смысловой дедуп** — сравниваем вектор с постами **того же канала за последние 24 часа**. Если очень похоже на уже имеющуюся новость (косинус выше порога) — это дубль по смыслу, карточка уходит в **`rejected`**. (Это ловит «одно событие разными словами» — то, что дедуп по ссылке не видит.) Не дубль → карточка сразу в **`pending`** — ещё **без бакета и без рерайта**.

**Классификация и рерайт автоматически не запускаются** — их по кнопке запускает человек из админки (см. раздел 3). Так контролируются расходы на OpenRouter и качество результата.

**Спец-путь `сво` (при рерайте):** минимальный рерайт — нейтральный пересказ официальной сводки, без формулировок «от себя» (юридический предохранитель + обязательная ручная вычитка).

**Если шаг упал** (автоматический или запущенный вручную) — карточка уходит в **`failed`**, текст ошибки пишется в `aiError`, карточка не теряется (из `failed` можно заново запустить классификацию или рерайт).

Итог нормального прохода: карточка в **`pending`** — ждёт решения человека.

---

## 3. Человек в админке (веб-интерфейс аппрува)

Главная страница админки — **каналы**: здесь же они создаются и редактируются (форма создания + карточки каналов; у каждой — редактирование конфига и тумблер `active`). Клик по карточке канала открывает список его постов.

Человек открывает `pending`-карточку и:

- **читает** текст и видит картинку по URL;
- **если бакета нет** — жмёт **«Классифицировать»** (`POST /posts/:id/classify`, ответ 202): локальная классификация по бакетам канала, карточка снова в `pending`, уже с бакетом; бакет можно поправить руками;
- **если бакет есть** — жмёт **«На рерайт»** (`POST /posts/:id/rewrite`, ответ 202): рерайт+перевод через OpenRouter по промпту бакета, карточка в `pending` с текстом. Рерайт без бакета невозможен — сервис ответит `409 rewrite_no_bucket`. Обе кнопки работают из `pending` и `failed`;
- **правит** заголовок/текст (`finalTitle`/`finalText`) и при желании бакет;
- **работает с картинкой:** может добавить свою (по URL), выбрать одну из нескольких или убрать вовсе (тогда пост станет текстовым);
- жмёт **«Заапрувить»**. Рерайт для аппрува не обязателен: если модератора устраивает исходный текст, можно публиковать его как есть.

**Аппрув = не финал, а «показать, как встанет в канал».** По кнопке сервис отправляет текущий текст + выбранную картинку в **служебный канал** (технический буфер) и разбирает ответ Telegram:
- есть картинка → получаем **`file_id`** (сохраняем его в карточке) + `previewMessageId`; человек видит превью «вот так встанет»;
- картинки нет → превью текстового поста.

Статус становится **`ready_to_publish`** — карточка встаёт в очередь публикации.

Ещё человек может:
- **«Отменить аппрув»** → карточка возвращается в `pending` (превью в служебке при этом не удаляем — там своё TTL-автоудаление);
- **«Удалить»** → карточка уходит в `rejected` (soft-delete, пропадает из рабочей выдачи);
- запустить рерайт повторно той же кнопкой **«На рерайт»** (доступна из `pending` и `failed`).

## 4. Публикация (выход: второй n8n-flow)

> Воркфлоу ещё не создан — ниже описан контракт, который для него готов на стороне сервиса.

Отдельный воркфлоу n8n работает **по расписанию каждого канала** (`channels.schedule`) и постит из очереди — не сразу пачкой, а ровным темпом:

1. `GET /posts/queue?channelId=…` — берёт готовые к публикации посты канала, **самые старые первыми** (по одному, ровный тайминг). В ответе на каждый пост уже лежит всё для постинга: готовый (HTML-экранированный) текст, `file_id` выбранной картинки и `mainChatId` основного канала.
2. **Постит в основной канал** этого канала:
   - есть `file_id` → `sendPhoto` (подпись ≤ 1024, HTML);
   - нет → `sendMessage` (≤ 4096);
   - если `sendPhoto` упал → фолбэк на `sendMessage` без картинки (пост не теряется).
3. После успеха дёргает `PATCH /posts/:id/published` — сервис ставит статус **`published`** и сохраняет `publishedMessageId`.

**Важно:** в основной канал постит именно n8n. Сервис в основной канал не ходит — только отдаёт очередь и принимает отметку об успехе.

---

## 5. Про Telegram: один бот, одна служебка, N каналов

- **Один бот на все каналы** (`BOT_TOKEN`). За счёт этого `file_id` картинки, полученный в служебке, валиден в любом основном канале — картинку не нужно перезаливать при публикации.
- **Одна общая служебка** (`SERVICE_CHAT_ID`) на все каналы — туда идут превью и она же играет роль CDN для картинок (`file_id`). Чистится только TTL-автоудалением по сроку, вручную не трогаем: фоновая джоба бэкенда раз в 5 минут удаляет превью спустя `previewTtl` минут канала (или дефолт `PREVIEW_TTL_DEFAULT` = 1440 минут) после аппрува.
- **N основных каналов** — у каждого своя строка в таблице `channels` со своим `mainChatId`, набором бакетов, промптами рерайта и расписанием. Классификатор и рерайт берут настройки из конфига канала, а не из хардкода — новую нишу можно завести, не трогая код. Заводятся и редактируются каналы через UI админки на главной странице (см. раздел 3).

## 6. Статусы карточки — что значит и что дальше

```
ingested ──▶ processing ──▶ pending ⇄ ready_to_publish ──▶ published
                 │             │  ↘
                 ▼             ▼   ↘
               failed       rejected (удаление)
```

| Статус | Что значит |
|---|---|
| `ingested` | сырая карточка от n8n, ИИ ещё не трогал |
| `processing` | идёт ИИ-обработка |
| `pending` | ждёт решения человека в админке; может быть ещё без бакета и без рерайта — классификацию и рерайт человек запускает кнопками (см. раздел 3) |
| `ready_to_publish` | человек заапрувил, превью сгенерировано, стоит в очереди публикации |
| `published` | опубликовано в основном канале |
| `rejected` | отклонено/удалено (в т.ч. смысловой дубль) |
| `failed` | ИИ упал, нужен разбор (`aiError`) |

Ключевой цикл — `pending ⇄ ready_to_publish`: аппрув двигает вперёд, «отменить аппрув» — назад. Все переходы проверяет сам сервис (неверный переход → ошибка `409 invalid_transition`).

## 7. Что может пойти не так (и куда смотреть)

- **Дубль по ссылке** на входе → `409` от `POST /posts` (n8n просто пропускает).
- **Смысловой дубль** → карточка в `rejected` (в `rejectReason` — на кого похоже).
- **Упал ИИ-шаг** (Ollama/OpenRouter недоступны, кривой ответ модели) → `failed` + `aiError`; из `failed` можно заново запустить классификацию или рерайт.
- **Рерайт по посту без бакета** → `409 rewrite_no_bucket` (сначала «Классифицировать»).
- **Картинка не прикрепилась** на аппруве → превью/публикация становятся текстовыми, пост не теряется.
- **Публикация с картинкой упала** → n8n фолбэчит на текст.

## 8. Как запустить и куда заходить

1. Скопировать `.env.example` → `.env` и заполнить: `OPENROUTER_API_KEY`, `BOT_TOKEN`, `SERVICE_CHAT_ID`, `N8N_ENCRYPTION_KEY`, `ADMIN_LOGIN`, `ADMIN_PASSWORD` (опционально `ADMIN_COOKIE_SECURE`, `REWRITE_MODEL` и др.).
2. `npm run start` — соберёт и поднимет все контейнеры (`docker compose up --build -d`) и напечатает адреса.

| Сервис | Куда заходить |
|---|---|
| **Админка** | http://localhost:8081 — вход по логину/паролю из env |
| **n8n** | http://localhost:5678 |
| **RSSHub** | http://localhost:1200 |
| **Ollama** | http://localhost:11434 |
| **Backend** | наружу **не публикуется**: с хоста — только через nginx (`/api` админки), внутри docker-сети — `backend:3000` |
| **Postgres** | внешнего порта нет (только внутри docker-сети) |

Остановить: `npm run stop`. Логи всех сервисов: `npm run logs`.

## 9. Вход в админку и защита API

- В админке есть страница **`/login`**; логин и пароль задаются в env **`ADMIN_LOGIN` / `ADMIN_PASSWORD`**. Если они не заданы — аутентификация выключена и админка открыта.
- После входа бэкенд ставит cookie-сессию **`admin_session`** (httpOnly, SameSite=Lax, срок 7 дней). Сессии живут в памяти бэкенда — рестарт контейнера разлогинивает.
- **nginx проверяет каждый запрос к `/api/*`** через `auth_request` → `GET /auth/check` на бэкенде; при `401` фронт уводит на `/login`.
- Бэкенд-роуты: `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, `GET /auth/check`.
- Для работы за HTTPS есть `ADMIN_COOKIE_SECURE=true` — включает secure-флаг куки.
- **n8n аутентификацию не проходит:** он ходит в бэкенд напрямую по docker-сети (`backend:3000`), минуя nginx.

---

*Компоненты: n8n (сбор) → **сервис** (хранение, ИИ, аппрув-API, админка, очередь) → n8n (публикация) → основной канал. Служебный канал — технический буфер для превью и `file_id`.*
