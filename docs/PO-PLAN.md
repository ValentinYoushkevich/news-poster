# ТЗ: сервис аппрува и публикации постов Telegram-канала

## 0. Контекст и назначение

Через **n8n** собирается контент для Telegram-канала новостей (RSS + Telegram-источники через RSSHub). Собранные карточки складываются в базу для обработки **сервисом аппрува**, который и разрабатываем.

**Назначение сервиса.** Принимать сырые карточки от n8n, прогонять ИИ-обработку (смысловой дедуп, классификация по бакетам, рерайт с переводом), давать человеку веб-интерфейс аппрува с правкой текста и картинки, генерировать превью поста в служебном канале (заливка → `file_id`), и отдавать готовые посты публикующей джобе, которая по расписанию постит их в основной канал.

**Стек.**
- Бэкенд: PostgreSQL + Prisma + Node.js + Express
- Фронтенд: PrimeVue + Vue 3 + Tailwind
- Внешние: n8n (оркестратор), Ollama (эмбеддинги, локально), OpenRouter (рерайт), Telegram — **один бот** на все каналы, **одна общая служебка** (превью/CDN картинок) + N основных каналов (публикация)

**Мультиканальность.** Сервис с самого начала рассчитан на несколько каналов (сейчас один, но механика заложена). Один канал = одна ниша со своим набором бакетов, промптами рерайта, расписанием и основным Telegram-каналом.

- **Один бот на все** — `botToken` глобальный (env). За счёт этого `file_id` из служебки валиден в любом основном канале.
- **Одна общая служебка** — `serviceChatId` глобальный (env). Превью всех каналов идут в неё.
- В строке канала (`channels`) хранится только его `mainChatId` + конфиг (бакеты, промпты, расписание).
- Роутинг: n8n проставляет `channelId` на каждой карточке при ingest.

**Границы.** Сервис — единственный владелец состояния и всей логики поверх постов. n8n не хранит состояние и не пишет в БД напрямую — только через REST.

| Компонент | Ответственность |
|---|---|
| **n8n (сбор)** | Фиды → нормализация → `POST /posts` |
| **Сервис** | Хранение, ИИ-обработка, аппрув-API, веб-админка, очередь публикации |
| **n8n (публикация)** | По расписанию тянет готовые посты → постит в основной канал → пишет статус назад |
| **Служебный канал** | Превью поста + CDN картинок (`file_id`). Чистится TTL-автоудалением, вручную не трогаем |

## 1. Модель данных

### 1.0. Глобальный конфиг (env, не в БД)

- `BOT_TOKEN` — один бот на все каналы
- `SERVICE_CHAT_ID` — общая служебка (превью + CDN картинок)

### 1.1. Таблица `channels`

Конфиг канала переезжает из хардкода в строку БД:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | BigInt PK | id канала |
| `name` | String | человекочитаемое имя |
| `mainChatId` | String | chat_id основного канала для публикации |
| `buckets` | Json | набор бакетов этого канала (`string[]`), напр. `["рф-внутр","сво","мир-с-рф","мир-без-рф"]` |
| `rewritePrompts` | Json | промпты/few-shot рерайта, per-bucket (у разных ниш свой голос) |
| `schedule` | String | расписание публикации (cron/интервал) |
| `previewTtl` | Int? | TTL превью в служебке для этого канала (или глобальный дефолт) |
| `active` | Boolean | канал включён |
| `createdAt` `updatedAt` | DateTime | |

Бакеты и промпты — **per-channel**: классификатор и рерайт берут список/шаблоны из конфига канала, а не из хардкода. Тех-канал в будущем получит свои бакеты, не трогая код.

### 1.2. Таблица `posts` (Prisma-модель):

| Поле | Тип | Назначение |
|---|---|---|
| `id` | BigInt PK | внутренний id |
| `channelId` | BigInt FK → channels | какому каналу принадлежит карточка; проставляет n8n при ingest |
| `source` | String | имя фида (rbc/guardian/bbc/lenta/…), от n8n |
| `sourceLang` | String | `ru` / `en` — драйвит перевод в рерайте |
| `link` | String | канонич. ссылка; уникальна **в паре с channelId** (см. ниже) |
| `guid` | String? | guid источника (резервный ключ) |
| `origTitle` | String | исходный заголовок |
| `origText` | String | исходный текст, почищенный от HTML/хвостов |
| `author` | String? | `creator`⧸`author`⧸`dc:creator`, схлопнуто, nullable |
| `categories` | Json | нормализованный `string[]` |
| `pubDate` | DateTime | из `isoDate` |
| `images` | Json | кандидаты: `[{url, type, origin, fileId, chosen}]` |
| `bucket` | String? | рф-внутр ⧸ сво ⧸ мир-с-рф ⧸ мир-без-рф, ставит классификатор |
| `embedding` | Json? | вектор для смыслового дедупа |
| `rewrittenTitle` | String? | результат ИИ |
| `rewrittenText` | String? | результат ИИ |
| `finalTitle` | String? | что публикуется; редактируется; дефолт = rewritten |
| `finalText` | String? | то же для тела |
| `status` | String | см. статусную модель |
| `previewMessageId` | BigInt? | id сообщения-превью в служебном канале |
| `publishedMessageId` | BigInt? | id сообщения в основном канале после публикации |
| `aiError` | String? | текст ошибки ИИ-шага |
| `rejectReason` | String? | причина отклонения |
| `createdAt` `updatedAt` `approvedAt` `publishedAt` | DateTime | тайминги |

Уникальность: `@@unique([channelId, link])` — **не глобальный `link @unique`**. Один источник может кормить несколько каналов, и одна ссылка легитимно уходит в каждый из них; дедуп по строке скоупится каналом.

Индексы: `(channelId, link)` unique, `(channelId, status, pubDate)` — под очередь публикации, `(channelId, bucket)`, `pubDate`.

**Картинки — почему массив.** Требование «оставить 1 из нескольких» + возможные источники с галереями. `chosen: true` помечает выбранную; `fileId` заполняется на аппруве (заливка в служебку). `origin` = `enclosure` | `content` | `uploaded` (загружена человеком вручную).

## 2. Статусная модель

```
ingested → processing → pending ⇄ ready_to_publish → published
                ↓          ↓  ↘
              failed   rejected (удаление)
```

| Статус | Смысл |
|---|---|
| `ingested` | сырая карточка от n8n, ИИ не трогал |
| `processing` | идёт ИИ-обработка |
| `pending` | ИИ отработал, ждёт человека в админке |
| `ready_to_publish` | человек заапрувил, превью сгенерировано, стоит в очереди публикации |
| `published` | ушёл в основной канал |
| `rejected` | удалён/отклонён |
| `failed` | ИИ упал, нужен разбор |

Переходы валидирует сервис. Ключевой цикл — `pending ⇄ ready_to_publish`: аппрув двигает вперёд, «отменить аппрув» возвращает назад.

## 3. Слой нормализации (ingest)

n8n шлёт `POST /posts` с сырым айтемом + `channelId`, `source`, `sourceLang`. Сервис приводит к карточке:

- **channelId** — обязателен; определяет канал, скоуп дедупа и набор бакетов/промптов для ИИ
- **author** = `creator || author || dc:creator || null`
- **categories** → плоский `string[]`: RBC уже строки; Guardian — `cat._` из объектов; BBC — пустой массив
- **origText** = `contentSnippet` → снять HTML, срезать хвост «Continue reading…» и мусор
- **pubDate** = `isoDate`
- **images**: `enclosure.url` → один кандидат; иначе `<img src>` из `content`; иначе пусто (text-only)
- **link** — строковый дедуп **в пределах channelId**; повторный `POST` той же пары (channelId, link) → `409`
- `enclosure.length` игнорировать (мусорный `"0"`)

## 4. Модуль ИИ-обработки

Асинхронный воркер (рерайт через OpenRouter имеет задержку — синхронно в HTTP-ответ не вешаем). Запускается на `ingested`, ведёт `processing → pending`.

Конвейер на карточку:

1. **Эмбеддинг** — Ollama, `bge-m3` (мультиязычная, лучше nomic на РФ-тексте) → `embedding`
2. **Смысловой дедуп** — косинус против постов **того же канала** за 24ч (`WHERE channelId = ? AND createdAt > now() - 24h`); дубль выше порога → отбрасываем. **Скоуп по каналу критичен:** без `channelId` в условии второй канал с пересекающимися источниками будет голодать — первый «съест» новость дедупом.
3. **Классификация бакета** — набор бакетов берётся из `channels.buckets` этого канала, не из хардкода
4. **Перевод** — только если `sourceLang = en`
5. **Рерайт** — OpenRouter, few-shot; промпт/примеры из `channels.rewritePrompts` per-bucket → `rewrittenTitle/Text`, копируются в `final*` как дефолт

**Спец-путь `сво`:** только официальные источники (белый список на стороне n8n), рерайт минимальный — «пересказ офиц. сводки», «по данным ведомства», без формулировок от себя. Юридический предохранитель; поверх — обязательная ручная вычитка.

Провайдеры за интерфейсом (сменить Ollama/OpenRouter конфигом). Ошибка шага → `failed` + `aiError`, карточка не теряется.

## 5. Аппрув: работа человека в админке

### 5.1. Просмотр карточки (`pending`)
- видит текст + картинку по исходному URL (превью)
- **правит текст** (`finalTitle`, `finalText`)
- **если картинки нет / ссылка битая** → кнопка **«Добавить картинку»**: загрузка своего файла (`origin=uploaded`)
- может **убрать картинку** → пост станет текстовым

### 5.2. Кнопка «Заапрувить» — генерация превью
Аппрув = не финал, а **показать, как встанет в канал**:
1. текущий текст + выбранная/загруженная картинка улетают в **служебный канал**
2. разбор ответа Telegram:
   - **есть `photo` → есть `file_id`** → сохраняем `fileId` в `images`, `previewMessageId`; человеку показываем превью «вот так встанет в канал» (картинка + текст)
   - **ответ без картинки** (не было / не прикрепилась) → превью текстового поста
3. статус → `ready_to_publish`
4. человек глазами видит финальный вид и подтверждает

### 5.3. «Отменить аппрув»
- `ready_to_publish → pending`
- сообщение-превью в служебке **не удаляем** — там TTL-автоудаление по сроку

### 5.4. «Удалить карточку»
- `→ rejected` (soft-delete), убирается из рабочей выдачи

## 6. REST API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/posts` | ingest от n8n (обяз. `channelId`); дедуп по (channelId, link) → 409; `ingested`, триггер ИИ |
| `GET` | `/posts` | список; фильтры `?channelId=&status=&bucket=&date=&source=&page=` |
| `GET`/`POST`/`PATCH` | `/channels` | CRUD каналов (конфиг: mainChatId, бакеты, промпты, расписание) |
| `GET` | `/posts/:id` | карточка |
| `PATCH` | `/posts/:id` | правка `finalTitle/finalText/bucket` |
| `POST` | `/posts/:id/images` | загрузить свою картинку (`origin=uploaded`) |
| `PATCH` | `/posts/:id/images/select` | выбрать одну / убрать картинку |
| `POST` | `/posts/:id/approve` | заапрувить: залить в служебку → `fileId` → `ready_to_publish` + превью |
| `POST` | `/posts/:id/unapprove` | откат `ready_to_publish → pending` |
| `DELETE`| `/posts/:id` | удалить (`rejected`, soft-delete) |
| `POST` | `/posts/:id/rewrite` | пере-запустить рерайт (idempotent, async) |
| `GET` | `/posts?status=ready_to_publish` | очередь для публикующей джобы |
| `PATCH` | `/posts/:id/published` | джоба: `→ published` + `publishedMessageId` |

## 7. Публикующая джоба (контракт с n8n)

Отдельный воркфлоу по расписанию, **на каждый канал по своему расписанию** из `channels.schedule` (посты уходят в очередь, а не сразу):

1. `GET /posts?channelId=X&status=ready_to_publish` (по одному, ORDER BY pubDate) — ровный тайминг
2. Публикация в **основной канал этого канала** (`channels.mainChatId`) по сохранённому `fileId`:
   - есть `fileId` → `sendPhoto` (caption ≤ 1024, `parse_mode=HTML`)
   - нет → `sendMessage` (≤ 4096)
3. Фолбэк: `sendPhoto` упал → `sendMessage` без картинки (пост не теряется)
4. Успех → `PATCH /posts/:id/published` + `publishedMessageId`

HTML-экранирование (`&`→`&amp;`, `<`→`&lt;`, `>`→`&gt;`) делает сервис при формировании `finalText`.

---

## 8. Служебный канал

- **Один общий на все каналы**, `SERVICE_CHAT_ID` в env. За счёт одного бота `file_id` из него валиден в любом основном канале.
- Роль: генерация превью + CDN картинок (`file_id`).
- Заполняется на аппруве, отдаёт `file_id` и `message_id`.
- Превью всех каналов идут вперемешку в одну служебку — приемлемо, т.к. это технический буфер, не рабочая выдача.
- **Чистка — только TTL-автоудалением по сроку.** Вручную/по отмене аппрува не удаляем.

## 9. Открытые развилки

1. **Эмбеддинг/дедуп** — оставляем в сервисе (рекомендация: история в БД) или в n8n. Рерайт — точно в сервисе.
2. **Перевод EN** — отдельным шагом или одним промптом «переведи+перепиши» (влияет на число вызовов OpenRouter).
3. **pgvector или Json** для `embedding` — при сотнях постов/сутки Json + брутфорс хватает.
4. **TTL служебного канала** — какой срок автоудаления ставим (сутки / несколько часов).
